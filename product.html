Performance

Built to pass Core Web Vitals, not just look fast.

Google measures three things when it decides whether your site is "fast": how quickly the main content appears, whether anything jumps around while it loads, and how quickly the page responds when someone taps something. All three affect both your ranking and whether a visitor sticks around long enough to call you.

The Targets

  • Main content on screen in under 2.5 seconds on a phone. That's Google's "Good" line, and every build is tested against it.
  • Nothing jumps around while it loads (layout shift under 0.1), so nobody taps the wrong button.
  • Taps answered straight away (under 200 milliseconds), even with the booking calendar on the page.

How We Get There

  • Every image is compressed and sized for the screen it's shown on — no full-resolution photos served to a phone.
  • Fonts are hosted with the site, not fetched from Google or anyone else — and the main body font loads with the page, so text shows straight away.
  • No page builder, no database, no plugins — just the code the page actually needs, and nothing extra slowing it down.
  • Third-party embeds only load once a visitor scrolls near them, not the moment the page opens.
Security

A static site has far less to attack.

Most small-business sites get compromised the same few ways: a leaked admin password, an outdated plugin, or a database that was never patched. A standard website built the way we build it has none of those doors. Custom systems, which do need a database, get a security audit before launch.

01

HTTPS everywhere, renewed automatically

Every page is served over HTTPS with a certificate that renews itself — no manual renewal to forget, no expired-certificate warning scaring visitors off.

02

No database, no admin login, nothing to break into

There's no login page for someone to guess their way into, and no database to leak or inject code through. The classic ways a small-business site gets hacked simply don't apply here.

03

Every change is tracked and reversible

The site is built under version control, so every edit is recorded. If anything ever needs undoing, it takes minutes, not a frantic phone call.

04

Only the outside code you ask for

Outside code is kept to what you ask for, like a booking calendar, or Google Analytics after visitors accept cookies. We don't add widgets you didn't ask for. Fewer scripts means less to attack and a faster page.

Standards

Readable by people, and by search engines.

A site that's easy for a screen reader to parse is usually also easy for Google to understand — the two go hand in hand more than people expect.

Accessibility

  • Text and background colours are checked against WCAG AA contrast ratios by calculation, not by eye.
  • Semantic, structured markup that screen readers can navigate properly, not just a visual layout.
  • Fully responsive: tested at phone, tablet and desktop sizes, and on a real phone.

Search (SEO)

  • Structured data included so Google can understand who you are, what you do, and where you work.
  • Proper page titles, descriptions, and a sitemap so search engines can find and index every page.
  • Fast load times aren't just nice to have — Core Web Vitals are one of the signals Google uses to rank pages.
How we check

Every build is tested before it goes live.

We don't take our own word for it. Each site is run through Google's own tools, then checked for accessibility and design with open-source tools.

Google's checks

  • PageSpeed Insights, on mobile and desktop: speed, accessibility, best practice and SEO scores.
  • Search Console, set up with you as the owner, so you see what Google sees.

Accessibility & design checks

  • Contrast worked out, not guessed: every text colour meets WCAG AA (4.5:1).
  • Keyboard-only run-through of every page, with a visible focus outline.
  • Buttons big enough for a thumb: at least 44px on a phone.
  • Open-source tools: Google Lighthouse, run on every page before launch.

Technical FAQs

The questions that come up once people see the detail.

Straight answers to the technical questions we get asked most.

Q1What if I want a blog or extra pages later?+

We add pages the same way the rest of the site is built — fast, static, no plugins. If you eventually need something that has to run on a server, like a members' area or a custom checkout, we tell you that upfront and scope it separately rather than bolting it onto a site that was never built for it.

Q2Do you handle cookie and GDPR compliance?+

Every site ships with a privacy policy, and we keep the number of third parties deliberately small — usually just a booking calendar and Google Analytics. Fewer third parties means less to disclose and less risk, not just a longer policy document.

Q3What if I need a contact form that emails me, or payment processing?+

Both are possible without adding a server or a database — a form service or a hosted checkout page can handle it directly from the browser. If what you need genuinely requires custom server-side logic, we'll say so plainly rather than force-fitting it.

Q4How do you check a site before it goes live?+

We run every page through the same tools Google uses to score sites, before launch and again after any change. The list is in How we check above. This site is held to the same standard we build for you.
